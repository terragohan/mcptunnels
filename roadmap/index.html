Roadmap

Where mcptunnels is headed. Roughly ordered; no dates — this is a spare-time project and priorities follow real user pain.

v0.1 — MVP (today)

Section titled “v0.1 — MVP (today)”
Shipped

The foundation that exists now: anonymous, ephemeral tunnels with zero setup.

One command

mcptunnel expose -- <cmd> spawns any stdio MCP server and gives it a public URL.

No accounts

No signup, no login. OAuth 2.1 is on by default behind a CLI-generated password; --no-auth for open URLs.

Ephemeral by design

Tunnels expire after 24 hours. A janitor sweeps expired tenants, and Ctrl-C deletes a tunnel immediately.

Self-hostable relay

tunneld is a single binary plus SQLite, with ACME TLS and Docker or bare-metal deployment.

Tested data plane

End-to-end tests cover the WebSocket + yamux proxy, stdio bridge, SSE streaming, and automatic agent reconnect.

Next: permanent tunnels

Section titled “Next: permanent tunnels”
Planned

The MVP’s ephemerality is the feature that lets us skip accounts — and the first thing real users will outgrow.

Named, stable URLs

Claim /<you>/<name> once and keep it across restarts, reboots, and laptop sleeps.

Minimal identity

The smallest possible account system, likely invite/token-based signup via the CLI — no web app.

Multiple services

One identity can host several services, each with its own stable URL and independent agent keys.

CLI lifecycle

List, rotate keys, revoke, and delete services directly from the command line.

Then: MCP servers as scalable HTTP services

Section titled “Then: MCP servers as scalable HTTP services”
Future

Today expose bolts a public URL onto a single local process. The bigger destination is making MCP servers easy to run and scale as Streamable HTTP services — not just reachable, but deployable.

stdio → HTTP framework

The bridge inside expose becomes a reusable library/thin runtime: take any stdio MCP server and serve it as a proper Streamable HTTP endpoint behind a load balancer.

Deployment targets

Opinionated recipes — and eventually adapters — for containers, VMs, and edge platforms like Cloudflare Workers.

Lifecycle handled once

Streamable HTTP sessions, stateless vs. stateful modes, and horizontal scaling semantics solved in one place instead of re-derived by every server author.

Graduation path

Develop against a quick tunnel on your laptop, then deploy the same server to real infrastructure with the same transport.

Later: richer OAuth

Section titled “Later: richer OAuth”
Future

Per-tunnel OAuth 2.1 (discovery metadata, DCR, PKCE) shipped with the MVP. What comes later:

Pluggable identity

Today it’s a per-tunnel password/login page; later, bring-your-own IdP (Google, GitHub, enterprise OIDC).

Audience isolation

Tokens scoped to a single tunnel so one compromised credential can’t roam.

Identity pass-through

Forward identity headers to the local server so it can make per-user decisions without implementing OAuth itself.

Explicit non-goals (for now)

  • Generic TCP/HTTP tunneling of non-MCP services (ngrok’s job, done well).
  • A hosted, billing-backed SaaS. (There is a default public relay at https://tunnel.mcptunnels.xyz for convenience — it’s free and best-effort, and self-hosting stays a first-class path.)
  • A web dashboard.

How to influence this

File an issue describing your use case — especially if the MVP’s 24h model is the thing blocking you. That’s the signal that permanent tunnels should move up.
